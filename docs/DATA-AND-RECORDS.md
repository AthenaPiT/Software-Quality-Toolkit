# 数据与记录管理规范（内部使用）

> 适用对象：使用 Software Quality Toolkit 管理实际项目的质量团队。
> 本文件是操作规范；界面内 `Data & Records → Safe-keeping guide` 是同一套规范的英文精简版。

## 一、一句话原则

**代码放 GitHub，真实数据不上 GitHub；`.sqt.json` 是唯一权威副本，浏览器只是编辑器。**

工具是一个本地 HTML 文件，双击即可运行，不需要服务器、不需要账号、不发起任何网络请求。
数据能否长期保存，不取决于 GitHub，而取决于你是否按时把快照存到公司允许的位置。

## 二、三层数据模型

| 层级 | 存在哪里 | 换电脑 / 清缓存后还在吗 | 作用 |
| --- | --- | --- | --- |
| **快照 `.sqt.json`** | 你指定的磁盘位置 | ✅ 在 | 权威副本、归档、交接、版本管理 |
| 浏览器工作副本 | `localStorage` | ❌ 不在 | 同一台机器上快速恢复现场 |
| 版本检查点 | `localStorage` | ❌ 不在 | 回滚几分钟内的误操作（最多 8 个） |

顶栏状态灯的含义：

| 显示 | 含义 | 该做什么 |
| --- | --- | --- |
| `Not backed up` | 从未导出过文件 | 立刻存第一份快照 |
| `Unsaved to file`（琥珀） | 有改动只存在于浏览器 | 收工前必须导出 |
| `Backed up 12 Nov, 22:31` | 已与文件同步 | 无需操作 |
| `Auto-saved to file` | 已关联文件，改动自动写回 | 无需操作（仅当次会话有效） |

> 界面里的「版本检查点」是浏览器内的后悔药，**不是备份**。清站点数据、换浏览器、IT 重装系统都会一起消失。

## 三、合规红线

1. **仓库设为 Private**，或使用公司 GitHub Enterprise / 内部 Git 服务。
2. **绝不提交真实快照与导出记录。** 仓库 `.gitignore` 已排除 `*.sqt.json`、`SQT_*.md`、`SQT_*.csv`；唯一允许入库的是 `examples/sample-workspace.sqt.json`（虚构示例）。
3. **不要把项目数据放进公开的 GitHub Pages。** Pages 只发布工具外壳，不发布数据；每位访客看到的仍是自己浏览器里的空工作区。
4. **Issue、PR、commit message 不要写**项目代号、供应商名称、缺陷数量、风险等级等内部信息。
5. 未经 IT 批准，不要使用外部网盘、个人云盘或在线表单承载项目数据。
6. 工具本身无埋点、无 CDN、无外部字体、无遥测；数据只在你主动导出文件时才离开浏览器。

## 四、存放位置怎么选

| 方案 | 优点 | 注意 |
| --- | --- | --- |
| **公司映射网络盘 / 部门共享目录** | 已有备份与权限体系，最省事 | 确认目录有版本保留策略 |
| **内部 Git 仓库（私有）** ⭐ | JSON 是纯文本，天然有 diff、历史、回滚、责任人 | 仓库必须私有；遵守公司留存与删除政策 |
| 公司许可的受管同步盘（OneDrive / SharePoint） | 自动同步、异地副本 | 避免两人同时改同一文件产生冲突副本 |
| 受控加密介质 / 归档 | 作为第二份异地副本 | 按公司资产与加密要求执行 |

推荐组合：**网络盘一份 + 本地工作副本一份**，重要节点（SOP、放行评审）再单独归档一份带日期的快照与 Quality Record。

## 五、日常操作流程

**首次启用**
1. 把整个文件夹放到受控目录，双击 `SoftwareQualityToolkit.html`。
2. `Data & Records → Backup & export` 设置 **Recorded by / author**（用姓名或工号，团队统一）。
3. `Safe-keeping guide → Clear samples` 清除示例项目。
4. 新建项目、建 Cluster / SWC，收工前存快照。

**每次工作收尾**
1. `Save snapshot to file`，得到 `SQT_YYYY-MM-DD_HHMMSS.sqt.json`。
2. 把文件从「下载」移到受控目录；**保留带日期的多份副本，不要只留一份**。
3. 需要评审留痕时，导出 `Quality Record (.md)` 与 `Node Register (.csv)` 一并归档。
4. 若用 Git 管理，提交快照（见下节）。

**评审 / 汇报**
- `Quality Record (.md)`：结构、计划、风险、活动完成度、完整变更日志，可直接转 PDF 附在会议纪要后。
- `Node Register (.csv)`：Excel 打开做筛选、统计、跟踪（UTF-8 BOM，中文不乱码）。
- `Change Log (.csv)`：谁在什么时候改了什么，用于追溯。

**换电脑 / 交接同事**
- 把整个文件夹打包成 zip 交给对方；对方双击 HTML，进 `Data & Records → Replace with file` 导入快照即可，无需安装任何东西。
- 只需追加某些项目时用 `Merge projects`（同名 ID 会自动分配新 ID，不会覆盖）。

**恢复到某次现场**
- 同一台机器：`Version history` 里选检查点 → `Restore`。
- 跨机器：用对应日期的 `.sqt.json` 导入。

## 六、用 Git 管理快照（推荐做法）

快照是纯文本 JSON，放进**私有** Git 仓库等于免费获得一套正式记录系统。

- 仓库结构建议按项目拆分，避免所有人挤在一个文件里：
  ```
  quality-records/
  ├── ACP-2026/
  │   └── SQT_2026-11-12_173000.sqt.json
  └── NVP-2027/
      └── SQT_2026-11-12_174500.sqt.json
  ```
- 提交信息写清「项目 + 阶段」，但不写敏感数值，例如：
  `ACP-2026: pre-SWA-review snapshot`
- 每次重要评审前打 tag：`swa-review-2026-11-20`。
- 需要对比两次现场时，用 Git diff 直接看 JSON 差异，或把两份快照都导出成 Quality Record 做人工比对。
- 不要 `force push` 覆盖历史；保留历史本身就是记录。
- 注意：这个仓库同样适用第三节的合规红线，且必须私有。

## 七、命名规范

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 快照 | `SQT_<日期>_<时分秒>.sqt.json`（工具自动生成） | `SQT_2026-11-12_173000.sqt.json` |
| 归档副本 | 在文件名后加阶段标识 | `SQT_2026-11-12_173000_PPA-gate.sqt.json` |
| 按项目归档 | 项目代号 / 文件名 | `ACP-2026/…` |
| 作者 | 团队统一（姓名缩写或工号） | `L.Rong` |

## 八、多人协作的限制与规避

当前是**单用户模型，后写入覆盖先写入**，没有锁、没有权限、没有审批服务器。

- ✅ 可行：一个快照文件一个负责人；不同项目拆成不同文件；异步交接（A 保存 → B 导入 → B 保存）。
- ⚠️ 谨慎：两人同时打开同一文件各自编辑再合并 —— 工具只支持「追加项目」的 Merge，不支持字段级冲突合并。
- ❌ 不可行：多人实时协同、按角色控制可见性、自动同步。
- 真需要这些能力时，才需要讨论后端；届时再评估公司能批准哪种形态（内网服务 / 私有化部署）。

## 九、常见问题

**Q：清了浏览器缓存，数据没了吗？**
只要按时导出过 `.sqt.json`，导入即可完整恢复（含变更日志）。没导出过则无法恢复本地工作副本。

**Q：快照文件被手工改过还能打开吗？**
能。工具会校验 FNV-1a 校验和并提示「文件在工具外被修改」，但不阻断导入——方便应急修数据。

**Q：`localStorage` 会不会不够用？**
约 5 MB 上限。工具只保留 8 个检查点、500 条日志；请定期归档并清理旧快照，不要把浏览器缓存当长期存储。

**Q：GitHub Pages 能不能当团队共用的系统？**
不能。它只发布工具外壳，数据仍在各自浏览器里、彼此不同步；且公开 Pages 不适合放公司数据。

**Q：样例项目怎么清掉？**
`Data & Records → Safe-keeping guide → Clear samples`（需二次确认），已保存的快照文件不受影响。
